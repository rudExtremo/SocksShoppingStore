# Архитектура

Классическое ASP.NET Core MVC‑приложение, разложенное по зонам ответственности:

- Controllers (`SocksShoppingStore/Controllers`): HTTP‑эндпоинты и координация UI
- Middleware (`SocksShoppingStore/Middleware`): сквозные аспекты пайплайна
- Services (`SocksShoppingStore/Services`): помощники локализации и опции
- Data (`SocksShoppingStore/Data`): источник данных в памяти
- Models (`SocksShoppingStore/Models`): доменные и view‑модели
- Views (`SocksShoppingStore/Views`): Razor UI; `wwwroot` — статические ресурсы

## Пайплайн запросов (Program.cs)

- HTTPS‑редирект и статика с кэш‑заголовками (7 дней)
- Локализация запросов (EN/RU) через провайдеры query и cookie
- Free‑tier guard: защита от случайных расходов/экспозиции деплоя
- Security headers (CSP, запрет фреймов, nosniff, referrer, permissions)
- Политика cookie (SameSite=Lax, HttpOnly, Secure по окружению)
- Ограничитель конкуренции (in‑process, быстрый отказ при насыщении)
- Ограничитель скорости (глобальный + именованный `api`) с дружелюбным телом 429
- Сессии и MVC‑роутинг
- Опер. эндпоинты: `GET /healthz`, `GET /robots.txt`, `GET /_status`

## Контроллеры

- `HomeController`: список каталога с поиском `q`; локализованные тексты
- `ProductsController`: детали товара (`/Products/Details?id=`)
- `ProductsApiController` (`[Route("api/products")]`): JSON‑выдача всех товаров; `[EnableRateLimiting("api")]`
- `CartController`: корзина в сессии (add/remove/delete/clear)
- `LegalController`: статичные страницы (TOS/Privacy)
- `LocalizationController`: POST‑переключение культуры с безопасным возвратом

## UI

- Поиск в шапке: компактный dropdown рядом с переключателем языка
- Фильтры каталога: Цена (min–max), Сортировка (кнопки с иконками)
- Ленивая загрузка: кнопка «Load more» запрашивает `/api/products?page=N&pageSize=M` и добавляет карточки на клиенте (без бесконечной прокрутки)

## Middleware

- `SecurityHeadersMiddleware`: CSP с nonce на запрос, запрет фреймов, `nosniff`, строгие referrer/permissions
- `FreeTierGuardMiddleware`: при включении и не‑allowlisted путях возвращает 503 (блокировка на Azure или целиком по настройке)
- `ConcurrencyLimiterMiddleware`: ограничение конкурентных запросов через `SemaphoreSlim`, при насыщении — 429

## Services и Data

- `ProductCatalogLocalizer`: подстановка имени/описания товара по культуре (EN по умолчанию, RU карта)
- `IProductRepository`: абстракция хранилища товаров
- `LegacyProductRepository`: обёртка над in‑memory списком (по умолчанию)
- `JsonProductRepository`: опциональное хранение в JSON (настраиваемый путь)
- `RequestMetrics`: скользящее окно латенсий + счётчики; доступно через `/_status`

## Конфигурация

`SocksShoppingStore/appsettings.json`:

- `FreeTier`: переключатель, детекция Azure, allowlist путей
- `RateLimiting`: `GlobalPerMinute`, `ApiPerMinute`
- `Concurrency`: `MaxConcurrentRequests`
- `Status`: `AllowIPs`, `LatencyWindowSize`
- `Legal`: имя контроллера и контактный email
- `Repository`: провайдер `InMemory|Json` и путь к JSON

## Архитектурная эволюция QA-фреймворка

Этот раздел описывает модернизацию инфраструктуры тестирования, выходя за рамки существующего стека и включая дисциплины, необходимые для современного QA-инженера.

### Улучшение автоматизации тестирования и отчетности

*   **Текущее состояние:** Проект использует NUnit для юнит- и интеграционных тестов, Selenium для UI-тестов и Allure Framework для отчетности.
*   **Стратегия модернизации:**
    *   **Усовершенствование структуры тестов:** Внедрение четкого разделения между типами тестов (Unit, Integration, API, UI) в структуре проекта `SocksShoppingStore.Tests`.
    *   **Использование расширенных возможностей Allure:** Выход за рамки базовых отчетов. Использование функций Allure, таких как Steps, Attachments (скриншоты при падении тестов), History и Categories для создания богатых, отлаживаемых и информативных отчетов.
    *   **Хостинг отчетов Allure на GitHub Pages:** Реализация CI/CD-процесса для автоматической генерации и публикации отчета Allure на публичный URL GitHub Pages после каждого запуска тестов. Это обеспечивает бесплатное, постоянное и легко распространяемое хранилище истории выполнения тестов.

### Интеграция тестирования производительности

*   **Цель:** Продемонстрировать способность выявлять узкие места в производительности даже на платформе с ограниченными ресурсами.
*   **Выбор инструмента:** Рекомендуется использовать **k6**. Он легковесный, ориентирован на разработчиков (тесты пишутся на JavaScript) и разработан для легкой интеграции в CI/CD пайплайны, что делает его идеальным для соблюдения лимитов бесплатных минут в GitHub Actions.
*   **Стратегия интеграции:**
    *   Разработка небольшого набора k6-скриптов, нацеленных на критически важные API (например, список продуктов, поиск, добавление в корзину).
    *   Интеграция шага выполнения k6 в рабочий процесс `dotnet-ci.yml`.
    *   Определение пороговых значений производительности (SLO) в k6-скриптах (например, время ответа p(95) < 500 мс). CI-задача будет завершаться неудачей, если эти пороги будут превышены, что демонстрирует проактивный контроль производительности.

### Внедрение тестирования безопасности (DevSecOps)

*   **Цель:** Сместить тестирование безопасности "влево" (Shift-Left Testing), интегрировав автоматизированные сканирования непосредственно в CI-пайплайн.
*   **Выбор инструмента:** Рекомендуется использовать **OWASP ZAP Baseline Scan** через его официальный GitHub Action (`zaproxy/action-baseline`). Это инструмент динамического тестирования безопасности приложений (DAST). Базовое сканирование выбрано вместо полного сканирования, поскольку оно неинтрузивно, значительно быстрее и идеально подходит для частых запусков в CI.
*   **Стратегия интеграции:**
    *   Добавление новой задачи в рабочий процесс `dotnet-ci.yml`, которая запускается после развертывания приложения в тестовом окружении.
    *   Action будет сканировать целевой URL и автоматически создавать/обновлять задачу (Issue) в GitHub с любыми найденными уязвимостями, демонстрируя замкнутый цикл обратной связи.
    *   Настройка `rules_file_name` для игнорирования известных ложных срабатываний, что показывает понимание практической сортировки проблем безопасности.

### Применение искусственного интеллекта в QA

*   **Цель:** Продемонстрировать практическое, ориентированное на ценность применение ИИ в тестировании.
*   **Практические применения:**
    *   **Генеративный ИИ для тестовых данных:** Использование большой языковой модели (LLM) для генерации разнообразного файла `products.json` с крайними случаями: длинные названия, специальные символы, отсутствующие URL изображений, отрицательные цены и т.д.
    *   **Самовосстанавливающиеся тесты с помощью ИИ:** В качестве исследовательской задачи, изучить библиотеки или написать собственный код на C#, который при возникновении `NoSuchElementException` в Selenium использует принципы ИИ для поиска альтернативных локаторов элемента (например, анализируя соседние элементы, текстовое содержимое или атрибуты).
    *   **Визуальное тестирование на основе ИИ:** Интеграция инструмента, который использует ИИ для визуального регрессионного тестирования, интеллектуально игнорируя незначительные различия в рендеринге и отмечая только существенные визуальные ошибки.
